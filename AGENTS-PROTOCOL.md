# Протокол работы агентов Satoru

Актуализирован 2026-09-07. Общий процесс для Claude, Codex и следующих агентов.
Вход — [AGENTS.md](./AGENTS.md); состояние — START-HERE.md и верх DEVLOG/BACKLOG.

## 1. Актуальный контекст и границы

До изменений проверь cwd, `git status --short --branch`, `git log -5 --oneline`,
выполни `git fetch origin master` и сравни HEAD с origin/master. Fetch не обновляет
рабочие файлы: изучи разницу и безопасно интегрируй актуальную базу до реализации.
Если сеть недоступна, обозначь границу актуальности; локальный анализ возможен,
но нельзя заявлять проверку свежего production.

Читай актуальный контракт функции до кода. Исторические handoff, архивы и старые записи
журнала — свидетельства прежних решений, а не новые команды. При расхождении кода,
требования и документации установи, что устарело; не выдавай план за готовую функцию.

Запрос построить/исправить выполняй до проверенного результата в рамках поручения.
Обычные детали решай самостоятельно по записанным требованиям; значимые предположения
обозначай. Сначала выполняй безопасную разрешённую часть. Спрашивай, когда неизвестный
выбор существенно меняет продукт, расходы, приватность, необратимые последствия или
выходит за поручение. Не вводи новое согласование для уже разрешённых действий.

Аудит, объяснение и диагностика разрешают чтение и безопасные проверки, но не исправление
всех найденных проблем. Явный баг тоже не расширяет аудит до реализации. Новые сообщения
учитывай сразу: уточнение сохраняет применимый контекст, отмена прекращает прежнюю работу.
Системные правила и permissions обязательны. Если skill/файл блокирует продолжение,
назови точный источник и правило; отличай требование от собственной интерпретации.

## 2. Параллельная работа и коммиты

Независимые задачи разных чатов веди в отдельных worktree/ветках. Можно продолжать свой
проверенный изолированный checkout. Явный запрос работать в общем checkout соблюдай
с точным контролем собственных изменений. Не удаляй и не prune чужие worktree.

Коммит содержит целостный проверяемый шаг: связанные файлы, необходимые тесты и docs вместе.
Незавершённую работу сохраняй в своей ветке с handoff; не отправляй неготовые куски в master.
Перед staging проверь diff/status; добавляй только явные свои пути и проверь staged diff.
Используй `apply_patch`; не откатывай и не присваивай чужие изменения.
Коммит не блокирует общий файл и не заменяет изоляцию.

Не удаляй index.lock автоматически: выясни путь Git metadata и наличие активной операции
или владельца блокировки. Если отсутствие владельца нельзя подтвердить, останови только
Git-операцию и сообщи причину. Не определяй занятость коллег чтением их частных сессий.

Подагентов запускай только при разрешении пользователя или применимых инструкций среды.
Когда это разрешено, делегируй независимую ограниченную задачу с явными файлами/контрактом
и ожидаемой проверкой. Один интегратор отвечает за общие файлы и релиз. Мелкую линейную
правку не дроби ради делегирования. Сообщения коллегам должны быть читаемы человеком.
Основной агент отвечает за проверку и интеграцию результата.

## 3. Архитектура и совместимость

Самостоятельную бизнес-логику выноси в чистые модули `public/*-v1.js` с существующим
browser/Node export-паттерном и поведенческими тестами. UI координирует и отображает.
Выделяй модуль по ответственности и тестируемости, не по числу строк. Сначала переиспользуй
существующую логику. Не дублируй решения движка в app.js ради удобства UI.

Изменение смысла существующего поля явно помечай «⚠️ Ломающее изменение» в контракте,
описывай затронутых потребителей в DEVLOG и сообщении коммита. Сохраняй совместимость,
где возможно без двусмысленной логики; иначе подготовь миграцию и проверки потребителей.

## 4. Проверки по риску

- Docs-only: diff, факты, ссылки и противоречия; существующие связанные проверки, если
  они проверяют изменённый контракт. Полный runtime suite без причины не требуется.
- Поведение: целевые unit/integration-тесты и `node --check` изменённых JS.
- UI: затронутый сценарий в браузере, desktop/mobile и empty/dense состояния по
  DESIGN-CRAFT-RULES.md. Применимые contrast, keyboard/touch, локализация и reduced-motion
  проверки обязательны. Unit-тесты не доказывают внешний вид.
- Данные/auth/экономика: негативные случаи, отказ записи, повтор, конфликт, восстановление
  и права доступа по контракту. Успех только после подтверждённого сохранения.
- Перед runtime-релизом: полный `npm test` на интегрированном кандидате и профильные gates.
  Runner: `node --test --test-concurrency=2 scripts/*.test.js`; не повышай параллельность
  серверных тестов без проверки изоляции.

Не создавай тесты низкорисковой правки, которые лишь повторяют её текст/реализацию.
Не ослабляй существующие проверки ради зелёного результата. После обязательных проверок
повторяй/расширяй их только при изменении кандидата, сбое или конкретном оставшемся риске.
Недоступную проверку назови явно; не подменяй её количеством пройденных unit-тестов.

## 5. Данные и тестовая среда

Тесты запускай с отдельным временным DATA_DIR и собственными fixtures. Не фильтруй реестр
живых пользователей ради уборки. Удалять можно только точные артефакты этой задачи в
проверенной изолированной среде. Не включай секреты и личный контент в логи/fixtures/handoff.
Прочитай актуальный контракт владельца данных: не обходи CAS/WAL прямым PUT, записью JSON
или Store._put. Фиксированная пауза не доказывает сохранение; ожидай receipt и повторное чтение.

Чужие пользовательские данные доступны только при явном разрешении владельца проекта
и в объёме задачи. Для диагностики предпочитай `/api/admin/crash-export/<id>`;
не используй общий `/api/admin/userdata` для получения дневников и рефлексий.

## 6. Service worker и публикация

При изменении app.js/index.html/styles.css или других кешируемых shell-файлов проверь
SHELL, подними CACHE и связанные immutable pins. Найди потребителей через `rg`; обнови
только проверенные активные ссылки и соответствующие тесты. Не делай слепую замену версии
по всему репозиторию: исторические fixtures могут намеренно хранить старые версии.
Не откатывай более свежую версию другого агента. Docs-only не требует PWA-бампа.

Для запрошенных изменений, включая документацию, по умолчанию:

1. Проверенный scoped commit; свежий origin/master и безопасная интеграция параллельных правок.
2. Fast-forward push в master без force-push. Если remote изменился, снова проверь интеграцию.
3. Проверка фактического deployment Railway и production; push сам по себе не означает деплой.
4. Отчёт: commit, deployment и выполненная проверка. Для docs-only достаточно статуса
   deployment соответствующего commit и доступности приложения; не выдумывай UI QA.

Явное «локально / без push / без деплоя» имеет приоритет. Не обходи упавшую проверку или
неготовый релиз. Понятный merge решай в своей ветке с проверкой; конфликт продуктовых
намерений уточняй. Не запускай deploy повторно, если автоматический уже идёт.

## 7. Документация и отчёт

DEVLOG: что изменено, почему, подтверждённые проверки и как продолжить.
BACKLOG: закрытие и новые конкретные открытые пункты. Не создавай вторую очередь в START-HERE.
Обновляй затронутые контракты и handoff в том же целостном коммите, что и работу.
Отчёт начинается с результата, затем существенные проверки и остаток. Простые слова,
минимум жаргона и повторов. Отличай локальную реализацию от опубликованной; не заявляй
весь продукт проверенным по одному экрану.
