# Browser boundary v260 / extension 0.6.0

Scope: finish the existing Chrome/Brave installation → connection → fresh status → one
real entry test path. This is a local candidate; publication/deployment is recorded by the
integrating release, not inferred from this document or the presence of a ZIP.

## Behavior and privacy contract

The existing bridge adds `checkedAt`, `enforcement` and `selfTest`. Existing version,
configured-site count and bounded active-session fields remain compatible. The page can
request status and open Options; it cannot request or confirm a test, change policies or
operate an account. New metadata stays in browser memory on the page; no telemetry/API
writer is added.

`enforcement.state` is `active`, `permission_removed`, `not_configured` or `unknown`.
It reads actual granted origins, dynamic DNR rules and registered exact-site scripts.
`active` means configured rules match applied browser state. It does not claim all websites
are protected or that permission cannot be withdrawn. Rules/API failures become `unknown`;
removing a grant is separate. Counts and `protectionEnabled` expose no site names.

The public helper validates/bounds the projection and expires confirmation after 90 seconds;
the app may use its existing stricter connection TTL. A cached/ready announcement is not
proof of applied protection. Old extension versions can still connect, with health unknown.

The Options test opens one enabled configured site's real homepage in a new tab. If a time
window currently permits that site, the test asks the person to finish it first. It never
changes a rule, session, reward or permission. The worker stores a single local pending
record before navigation; only the matching top-level gate/block response from that exact
tab can confirm it. A foreign page, iframe, different tab or unmatched boundary cannot.
The success notice appears after storage succeeds. Pending times out after 60 seconds;
changed rules/version makes the prior result `outdated`. Private rules/fingerprint/tab IDs
are never in the public result. A failed pre-navigation write closes only the new test tab.

`selfTest` is `{ state: never|pending|passed|failed|outdated, checkedAt: ISO|null }`.
This proves entry into one configured site, not timer expiry or every other site. The UI
says that directly, including that the chosen site may load if blocking fails. The gate
offers a return to the existing connection page after a persisted result.

## Automated and browser checks

- Focused Node gate: **96/96 PASS**, no skips. Command:
  `node --test --test-concurrency=2 scripts/browser-companion*.test.js extensions/satoru-attention/*.test.js`.
- Worker tests execute the real service-worker functions with isolated platform fixtures:
  applied/readback drift, revoked grants/API failure, exact-tab/top-level receipts, bridge
  write denial, lost storage, active-window refusal, timeout, worker replacement and changed
  configuration. Old package tests keep their original artifact versions.
- ZIP gate compares every runtime source/hash with the actual archive and checks unchanged
  permission arrays against v215. All four v260 aliases have identical bytes.
- Real disposable **Chrome 153.0.8010.37** and **Brave Chromium 152.0.7977.83** profiles:
  save a synthetic exact-site rule, real DNR navigation to the local gate, durable success
  receipt, 375px Options/gate without horizontal overflow, reduced motion, actual bridge on
  locally fulfilled production-origin files, and **20 landing variants per browser**
  (RU/EN/DE/UK/ES × dark/light × 375/1280px). No page errors in either receipt.
- Both browsers acknowledged an actual MV3 worker-target close request; subsequent
  `GET_HEALTH` returned applied rules and the saved receipt. Target IDs can be reused, so
  the report does not infer a new process merely from its ID.
- Actual Chrome screenshots were visually inspected: connection mobile, settings and gate.
  Store icon/promo exports preserve the existing mark and exact copy; dimensions and hashes
  are in `store-kit-v260/store-assets.json`.

The browser fixture changes only its temporary manifest to grant HTTP/HTTPS
`boundary.satoru.test/*`, avoiding a real website and native permission prompt. All public
landing responses are fulfilled from local files. No real account/profile/site was used.
These results do **not** verify the actual optional-permission consent dialog, owner’s
ordinary Brave installation, natural overnight sleep, signed install/update or production.

`chrome.runtime.reload()` disabled/closed the automation-loaded unpacked fixture in both
browsers. Ordinary user Reload is therefore **not verified**, and this probe is not reported
as a passing gate. It remains in both browser receipts alongside the signed-update gate.

Reproduce with `scripts/qa-browser-companion-v260.cjs chrome` or `brave`; provide Playwright
through `SATORU_PLAYWRIGHT_MODULE` (or the normal Node module path). Optional
`SATORU_BROWSER_EXECUTABLE` selects a test browser binary. The script creates/removes only
its exact temporary profile and writes the scoped QA receipts/screenshots. Chrome uses the
documented browser-level `Extensions.loadUnpacked` protocol; Brave uses its supported
unpacked-loading flags. Do not point this harness at an existing user profile.
