## 0. База, и что изменилось под ней по дороге

следующего `git fetch` — ровно то, о чём предупреждает `AGENTS-PROTOCOL.md`, правило 1.5.

### Сверка с §3 критического пути

`PRODUCT-CRITICAL-PATH-2026-09.md` §3 просит ровно три события — они и реализованы:

| §3 критического пути | Capability |
|---|---|
| «Подошёл согласованный рабочий блок → точная задача и её маленький старт» | `planned-start` |
| «Подошло выбранное завершение вечера → вопрос, чем человек занят; планирование завтра не путать с продолжением работы; срочность обсуждать, не конфисковывать план» | `evening-close` |
| «Подтверждённое выпадение/остановка → один подходящий возврат, а не список инструментов» | `after-lapse-return` |

Названные там же случаи приёмки закрыты кейсами: «я планирую завтра» — `ev-07`; «не хочу» —
`x-06` (серия отказов); «не знаю как» — `al-06` (один вопрос вместо выдуманного занятия);
план отсутствует — `ps-11` и `ps-07`; провайдер недоступен — `x-08`; prompt injection —
`x-07`; повтор push/card — `x-05` и тест идемпотентности.

«Срочность обсуждать, не конфисковывать план» — это `ps-07`: подтверждённый дедлайн
усиливает существующий ход, но при отсутствии сохранённой записи ответ остаётся молчанием.

### Что осталось допущением

1. **`FirstValue`** модулем в репозитории по-прежнему не является. Смоделирован как булев
   вход `firstValue.pending`; адаптер обязан его посчитать.
2. **`morning-recovery` остаётся единственной capability рантайма.** Три хода этого пакета

## 1. Что делает модуль

Отвечает на один вопрос: **какой ровно один ход уместен прямо сейчас — или молчание.**

Не делает: не рисует, не пишет в сторы, не доставляет, не формулирует текст (наружу идут
только locale keys), не создаёт второй план/календарь/трекер/валюту, не ходит в сеть, не
читает DOM, `State` и часы.

Три хода:

| id | Боль | Когда | Что предлагает |
|---|---|---|---|
| `after-lapse-return` | BH-04 | ≤3 ч после **подтверждённого** выпадения | минимум по исходному делу, иначе конечный отдых, иначе один вопрос |
| `planned-start` | BH-01 | −10…+45 мин от сохранённого времени входа | открыть **конкретную сохранённую** запись |
| `evening-close` | BH-06 | 0…+120 мин после собственной вечерней границы | вечерний переход + один вопрос о контексте |

### Как это не пересекается с `morning-recovery` из v212

`morning-recovery` ловит **следующее утро после вчерашнего повода** (05:00–13:00, повод от
`prevDay`). `after-lapse-return` ловит **тот же день, в течение трёх часов после эпизода**.
Окна не пересекаются по построению: событие, на которое смотрит один, для другого уже вне
окна. Проверено кейсом `al-12-window-expired`.

## 2. API

```js
const M = require('./public/secretary-next-moves-v2.js');   // или globalThis.SecretaryNextMovesV2
```

### `decide(input) → result`

```js
M.decide({
  // обязательное
  now: '2026-09-09T07:30:00.000Z',   // строгий ISO с зоной; модуль не знает «сейчас» сам
  today: '2026-09-09',               // локальный день; обязан совпасть с now+offset
  utcOffsetMinutes: 120,             // local = UTC + offset
  invocation: 'app_open',            // | 'scheduler' | 'manual' — как в рантайме
  availableChannels: ['card', 'push'],
  ledger: M.emptyLedger(),           // серверная проекция выдачи

  // необязательное
  preferredChannel: 'card',
  dayClosed: false,                  // строго boolean или отсутствует

  // блокировки (строго boolean внутри)
  activeSession: { active: false },   // глушит советы, но НЕ вечернюю границу
  guide: { active: false },           // глушит всё
  firstValue: { pending: false },     // глушит всё

  // проекции — каждая со своим observedAt
  plannedStart: { taskRef, plannedAtLocal: 'HH:MM', precision, startedToday, doneToday, minimumRef, observedAt },
  eveningContract: { configured: true, eveningTimeLocal: 'HH:MM', observedAt },
  tonightSchedule: { busyUntilLocal: 'HH:MM', observedAt },
  lapse: { confirmed: true, source, eventKey, day, endedAt, originalRef, originalStillActionable, screenEpisode, observedAt },
  habitMinimum: { habitRef, twoMin, observedAt },
  restMenu: { recipeRef, minutes, screenMode, observedAt },
  commitmentItems: [/* результат CommitmentV1.dueOn(state, today, mode) */],
  externalDeadline: { day, source: 'user_confirmed', observedAt },
});
```

Результат:

```js
{ ok: true, offer: null, silence: { reason: 'nothing_eligible' }, trace: [...] }
{ ok: true, offer: { /* см. ниже */ }, silence: null, trace: [...] }
{ ok: false, error: 'invalid_ledger' }
```

`trace` — **только диагностика**. Записи имеют ровно три поля `{capabilityId, decision, code}`;
ни текста, ни action, ни label в них нет, поэтому «показать заодно вторым» физически нечего.

### Форма хода

```js
{
  version: 2,
  offerId: 'after-lapse-return|2026-09-09|attention.escaped|2026-09-09|policy_4f',
  capabilityId: 'after-lapse-return',
  pain: 'BH-04',
  action: { type: 'task_open_prepared', args: { targetRef, size: 'minimum', day } },
  channel: 'card',                       // ровно один, не массив

  reasonCode: 'return_after_confirmed_escape',

  copy: { eyebrowKey, titleKey, bodyKey, questionKey, reasonKey },
  primary: { id: 'primary', labelKey, action },
  alternatives: [ { id, labelKey, action, disclosure: true } ],   // 0..2
  dismiss: { id: 'dismiss', labelKey: 'common.not_now', action: {...} },
  boundary: null | { atLocal: '22:00' },
  finite: null | { minutes: 20, endsAtLocal: '23:20' },
  closesDay: false,
  plansTomorrow: false,
```

### Остальные функции

| Функция | Назначение |
|---|---|
| `emptyLedger()` / `sanitizeLedger(raw)` | канонический ledger; `null` = повреждён (fail-closed) |
| `mark(ledger, offer, outcome, nowIso)` | `{ok, ledger, changed}`; outcome ∈ `offered\|accepted\|dismissed\|expired` |
| `suppressionFor(ledger, capabilityId, today)` | `{suppressed, until, reason}` |

| `cooldownKeyOf`, `isDay`, `addDays`, `parseIso`, `isoFromEpoch`, `localParts` | календарь без `Date` |

## 3. Ошибки

`decide` возвращает `{ok:false, error}` и **никаких side effects**:

| error | Когда |
|---|---|
| `invalid_time` | `now` не строгий ISO с зоной |
| `invalid_day` | `today` невозможен календарно, либо расходится с `now + utcOffsetMinutes` |
| `invalid_offset` | сдвиг не целый или вне ±840 мин |
| `invalid_invocation` | вызов не из закрытого списка (в частности «на рендер») |
| `invalid_channels` | `availableChannels` пуст |
| `invalid_ledger` | ledger повреждён — **не** подменяется пустым |
| `invalid_day_state` | `dayClosed` не boolean |
| `invalid_flag` | `activeSession.active` / `guide.active` / `firstValue.pending` не boolean |

Логика последних двух: нечёткий флаг — это неисправность адаптера. Считать его отсутствием
блокировки значило бы заговорить поверх активной сессии, поэтому он останавливает выбор.

`mark` дополнительно отдаёт `invalid_offer`, `invalid_outcome`, `unknown_capability`,
`cooldown_taken` (второй `offerId` на тот же `cooldownKey` в тот же день) и `terminal_state`
(попытка переписать завершённый исход).

## 4. Сохранение

Модуль **ничего не сохраняет**. Он читает проекцию ledger и возвращает новую версию из
`mark()`; писать обязан владелец — server secretary ledger из `SECRETARY-ROUTER-V212-INTEGRATION.md` §11.

```js
{
  version: 2,
  offers: { '<cooldownKey>': { offerId, at, state } },
  capabilities: { '<capabilityId>': { dismissedInARow, ignoredInARow, suppressedUntil, suppressReason } }
}
```

Правила:

- **Ложится в существующий envelope**, отдельного файла не заводить. Предлагаемое место —
  `data/users/<id>/secretary.json` → новый ключ `nextMoves` рядом с `events/ledger/recovery/experiment`.
  Второй store — это второй источник правды и рассинхрон при export/delete.
- Повреждённый файл **не перезаписывается пустым**: пустой означал бы «сегодня не говорили»
  и заново открыл бы уже отклонённое предложение.
- Запись идёт в тот же account export и тот же cascade delete, что и остальной `secretary`.
- Generic `PUT /api/data/*`, клиентский snapshot, импорт и AI-action не имеют права писать
  сюда: cooldown и suppression — это авторитет молчания, а не пользовательские настройки.
- `dismissedInARow`/`ignoredInARow` — счётчики поведения предложения, не человека. В экспорт
  идут, в лидерборд/Tribe/аналитику — нет.

Ротация: строки `offers` старше 30 дней можно удалять; `capabilities` — нет, там живут
активные паузы.

## 5. Как принимаются решения

### Свежесть

У каждой проекции обязателен `observedAt`. Просрочка сверх `cap.maxStalenessMinutes`
(`planned-start` 180 мин, остальные 240) = **unknown → отказ**, а не «плана нет».
Проекция из будущего (>60 с вперёд) тоже отвергается.

### Часовой пояс

Единственный источник — `utcOffsetMinutes`, семантика `local = UTC + offset` как в v212 §4.3.
Календарь считается своей арифметикой (`days_from_civil`), поэтому `2026-02-30` отвергается,
а не превращается в март. `Date` в модуле не используется вообще — это проверяет тест по исходнику.

### Уверенность и право спросить

| Ход | Уверенность | Почему |
|---|---|---|
| `after-lapse-return` | 0.9 / 0.8 | собственные слова человека / измеренная граница |
| `after-lapse-return` (нет ни дела, ни отдыха) | 0.5 | данных на ход нет → один вопрос |
| `planned-start` (точное сохранённое время) | 0.8 | факт о сегодня |
| `planned-start` + подтверждённый дедлайн сегодня | 0.9 | срочность усиливает существующий ход |
| `planned-start` («обычно по будням») | 0.5 | это не факт о сегодня → один вопрос |
| `evening-close` | 0.85 | подтверждённая настройка + пройденная граница |

Ниже `ASK_BELOW = 0.6` ход обязан стать `ask_one_question`: `mode:'ask'`, `bodyKey: null`,
`questionKey` заполнен. План до ответа не показывается.

### Cooldown и подавление

- Cooldown — дневной, ключ `<capabilityId>|<today>`, общий для принятия и отказа.
- 3 отказа подряд → пауза 14 дней, `reason: 'repeatedly_not_useful'`.
- 3 показа без ответа (`expired`) подряд → пауза 7 дней, `reason: 'never_answered'`.
- Принятие обнуляет обе серии.

Константы `DISMISS_STREAK_LIMIT/SUPPRESS_DAYS`, `IGNORE_*` вынесены в экспорт — это ручки
владельца, а не спрятанная в коде политика.

### Конфликты

Порядок жёсткий и именованный, не только числовой:

1. **Блокировки.** Гайд и первая ценность глушат всё: это короткие обучающие контуры,
   перебивать их нечем и незачем (`guide_active`, `first_value_pending`).

   Активная сессия и закрытый день глушат **советы**, но не назначенное человеком
   напоминание. «День уже закрыл, а работаю дальше» — это ровно тот случай, ради которого
   вечерняя граница существует; промолчать в нём значит отменить его собственную настройку
   в самый нужный момент. Поэтому при `activeSession` и `dayClosed` продолжают
   рассматриваться только `userScheduled` capability, а прочие уходят в `trace` с кодом
   `not_user_scheduled`. Если ни одна не подошла — молчание с исходной причиной.

   Перебивать работу при этом нельзя: пока идёт сессия, ход приходит с `interrupt: false`
   и `deferUntil: 'session_end'`. Показать его после конца сессии — работа UI; движок лишь
   говорит, что прерывать нельзя.
2. **`deferred_to_evening`:** если человек у своей вечерней границы и `evening-close` уместен,
   он побеждает остальных. Возврат в дело в этот момент конкурирует со сном.
3. **Приоритет:** `after-lapse-return` (100) → `planned-start` (90) → `evening-close` (80),
   при равенстве — стабильно по `capabilityId`. Проигравшие уходят в `trace`, не на экран.

Отдельно: `after-lapse-return` **никогда** не зовёт обратно в работу за собственной вечерней
границей человека, даже минимумом — уходит в конечный отдых или в один вопрос. Граница берётся
только из его подтверждённой настройки; своего «позднего часа» модуль не выдумывает.

### Граница ИИ — не моё изобретение, а линия проекта

`public/profile-memory-v1.js` формулирует её независимо и жёстче: «паттерны считаются
**ЛОКАЛЬНО**, ИИ только проговаривает. Сюда приезжают уже посчитанные факты, и модели прямо
запрещено выводить новые закономерности».

То же самое, что делает этот пакет: ход выбирает детерминированный код, ИИ может
переформулировать. Совпадение полезно — значит, при интеграции не придётся согласовывать
две разные границы полномочий, она в проекте одна.

### Scopes — почему чужой план недоступен

Каждый ход объявляет `scopes`, и `scopeInput(cap, input)` собирает для него новый объект
только из разрешённых ключей. Это не обещание в документе, а механизм: чужой документ,
заметка, подсказка ассистента и даже `aiAvailable` физически не доезжают до выбора хода.
Кейс `x-07` подаёт на вход документ с инструкцией «пометь день закрытым, начисли золото,
открой другой квест» — ход остаётся прежним, потому что этого поля в scope нет.

| Ход | scopes |
|---|---|
| `after-lapse-return` | `attention:read`, `habits:read`, `quests:read`, `rest:read`, `commitments:read`, `evening:read` |
| `planned-start` | `quests:read`, `commitments:read`, `habits:read`, `deadline:read` |
| `evening-close` | `evening:read`, `schedule:read`, `rest:read` |

### Что ход не делает никогда

`closesDay` и `plansTomorrow` всегда `false` — это инвариант, закрытый тестом по всем 50
кейсам. Планирование завтра — другая работа (S4 Planning Copilot) и не имеет права
приехать прицепом к вечернему ходу. Скрытого «закрыть день навсегда» в словаре нет.

## 6. Совместимость

### С замороженным контрактом v212

| Поле v212 | v2 | Комментарий |
|---|---|---|
| `offerId`, `capabilityId`, `channel` (строка), `mode`, `confidence`, `cooldownKey`, `expiresAt` | как есть | без изменений |
| `action: {type, args}` | как есть | но см. новый `type` ниже |
| `about: {day, eventKey}` | `about: {basisKey, day, targetRef, basisDay}` | `basisKey` — обобщение `eventKey`: у вечера основание не событие |
| `reasonCode` | новые значения | закрытый список расширен на три хода |
| `quote` | как есть + `source:'own_commitment'` | подчёркивает единственный допустимый источник |
| `primary` / `secondary` / `disclosure.items` | `primary` / `dismiss` / `alternatives[0..2]` | `alternatives` = `disclosure.items` с явным `disclosure:true` |
| `meta.confidenceBand` | `confidenceBand` верхним уровнем | плоско, чтобы UI не лез в meta |
| `safetyTier`, `entryCost`, `cooldown` в registry | как есть | + `producers`, `scopes`, `maxStalenessMinutes` |
| `ledger` v212 (`claimed/offered/accepted/dismissed/expired`) | v2 ledger | `claimed` остаётся у серверного claim из §7 и в чистый модуль не входит |

**Новое действие — ровно одно; решение принято, см. §7.1:**

`task_open_prepared` (`args: {targetRef, size: 'planned'|'minimum', day}`). Его нет в v212,
потому что «открыть конкретную сохранённую запись» не выражается ни одним из четырёх
существующих: `recovery_day_open` означает другое, `rest_start_prepared` — отдых. Класс
безопасности тот же — `reversible_open`, ничего разрушительного/платёжного/социального.
Модуль экспортирует `PROPOSED_ACTIONS` отдельно, и тест падает, если новых действий станет
больше одного. Решение по этому действию закрыто; повторное согласование не требуется.
Первый runtime-срез after-lapse-return опубликован в v254.

### С историческим runtime (`public/secretary-router-v1.js` до v254)

Рантайм за время работы над пакетом переписан и закрыл большую часть дефектов §12: он
переименован в `morning-recovery` (№13), отдаёт один канал (№10), требует `invocation`
(№14), использует `dayClosed` (№9), проверяет календарь round-trip (№2), не подменяет
неверное время системными часами (№8), а `secretary-events-v1.js` разделил
`normalizeIngress` / `sanitizeEvent` (№1) — числовые поля события больше не обнуляются
на round-trip. **Проверено на `6da8376`; `secretary-router-v1.js` и `secretary-events-v1.js` с v250 не менялись.**

Остаточные различия, из-за которых нужен адаптер:

| Что | Рантайм v250 | v2 | Что делает интегратор |
|---|---|---|---|
| контракт вызова | `INVOCATIONS = ['app_open','scheduler','manual']` | те же значения дословно | ничего: намеренно совпадает |
| id capability | `capability` | `capabilityId` | `toLegacyOfferV1()` переименовывает |
| канал | `channels: [один]` — массив из одного | `channel: 'card'` — строка | адаптер заворачивает в массив |
| низкая уверенность | `askOnly: true` | `mode: 'ask'` | адаптер переводит |
| причина | `reason` | `reasonCode` | адаптер переводит |
| `about` | `{day, eventKey}` | `{basisKey, day, targetRef, basisDay}` | `eventKey ← basisKey` |
| словарь действий | 4 действия v212 | + `task_open_prepared` | **решение владельца, §7.1** |

**Дефект §12 №15 закрыт в v254.** Исторически в `next()` на v250 стояло
`sanitizeLedger(inp.ledger) || emptyLedger()`, то есть испорченный файл молча становится
пустым — а пустой означает «сегодня ещё не говорили» и заново открывает уже отклонённое
предложение. Рядом: `next()` возвращает `null` и на молчание, и на некорректный вход, так
что вызывающий не отличает «хода нет» от «данные сломаны».

v2 этот дефект не наследует: повреждённый ledger даёт `{ok:false, error:'invalid_ledger'}`,
а молчание — отдельный `{ok:true, offer:null, silence:{reason}}`. Это не мой файл, поэтому
пакет фиксировал факт для интегратора. Интегратор исправил reader и server/UI recovery
в v254; актуальное поведение описано в SECRETARY-NEXT-MOVES-TRANSPORT-V1.md.

`toLegacyOfferV1(offer)` возвращает `{ok:false, error:'action_not_in_v1', action}` для
`task_open_prepared` — то есть адаптер сам сообщает, какой ход текущий рантайм доставить
не может. Это исполняемая часть таблицы, а не только её описание.

## 7. Решения — приняты интегратором 09.09.2026

Раздел был списком вопросов; ниже ответы и что из них следует для кода.

### 7.1. `task_open_prepared` — да, это правильное расширение

**Отдельное действие, не переименование «Дня восстановления».** Оно открывает конкретное
существующее дело пользователя с подготовленным входом. Границы, названные при согласовании
и обязательные к реализации:

- проверка владельца записи и её актуальности перед открытием;
- **никаких** автоматических переносов, завершений, начислений и запуска таймера;
- **открытие дела не равно согласию начать сессию** — это отдельное решение человека;
- замороженный v212 сохраняется как есть, расширение оформляется явной новой версией
  словаря, а не правкой v212 на месте.

Policy уже соответствует: действие только открывает (`safetyTier: 'reversible_open'`),
ничего не пишет и не запускает; таймера и начислений в выдаче нет по построению, это
закрыто тестом на отсутствие экономики. Executor обязан соблюсти те же границы.

### 7.2. Канал — карточка первой, нейтральный push следующим

Карточка — первый рабочий канал, но **не окончательное решение**: внешняя поддержка была
прямым запросом. Следующий канал — нейтральный push по согласию, который открывает
конкретное дело **после входа в приложение**. Название дела на заблокированном экране по
умолчанию не раскрывается.

В `CAPABILITIES` у `planned-start` сейчас `allowedChannels: ['card']` — это первый шаг,
а не постоянное ограничение. При добавлении push менять надо только эту строку; правило
«push не называет дело» уже записано в контракте доставки.

### 7.3. Пороги — стартовые гипотезы, с двумя поправками, которые уже внесены

- **Отказ приглушает конкретный тип предложения, а не всего секретаря.** Так и было:
  подавление хранится и применяется по `capabilityId`, общего выключателя нет.
- **Назначенные пользователем напоминания не исчезают из-за игнорирования советов.**
  Это была настоящая ошибка, и она исправлена: `evening-close` помечен `userScheduled: true`
  и не накапливает серий отказа и молчания. Вечерняя граница — настройка человека, а не
  совет Тени, и проигнорированный совет не имеет права её отменить. Дневной cooldown
  остаётся. Закрыто отдельным тестом.

Остальные числа (3 отказа → 14 дней, 3 игнора → 7 дней, окно −10…+45 мин) остаются
стартовыми гипотезами и вынесены в экспорт как ручки.

### 7.4. Что осталось за владельцем

Переименование `morning-after-overrun` → `morning-recovery` в рантайме **уже выполнено**
в v250. Из прежнего списка открытым остаётся только вопрос вкуса про «я горжусь тобой» —
он относится к копирайтингу, а не к этому модулю (см. `CONTENT-VOICE-LORE-V1.md`).

## 8. Что реально нужно построить, чтобы это заработало

Честный список отсутствующего. Модуль готов; **функция не работает**, пока этого нет.

### Producers (проекции) — ничего из этого сейчас не существует

| Проекция | Источник | Чего не хватает |
|---|---|---|
| `plannedStart` | `State.tasks` | поле **уже есть**: `task.startTime` (`HH:MM`, шаг 15 мин, ставится перетаскиванием в Календаре) + `task.date`. Нужен только проектор `tasks → {taskRef, plannedAtLocal, doneToday}` с `observedAt`. Открытый вопрос — `startedToday`: признака «начал» у задачи нет (есть только `done`/`completedAt`), поэтому либо он всегда `false`, либо его нужно выводить из активной Attention-сессии, привязанной к задаче. `precision:'exact_time'` производится из `startTime`; `weekday_pattern` пока производить не из чего — повторяющихся квестов с временем в модели нет, и это значение зарезервировано. |

### Delivery adapters

- **Серверный store**: ключ `nextMoves` в `data/users/<id>/secretary.json`, atomic write +
  backup + write guard, revision/seq guard, участие в export/delete.
- **Атомарный channel claim** из v212 §7 — без него гонка «открытая вкладка × push ×
  расширение × второе устройство» покажет два хода. Чистый ledger от этого не защищает.
- **Card surface**: одна поверхность Тени, `primary` + `dismiss` равноправной кнопкой,
  `alternatives` свёрнуты под «Другая поддержка». Место есть — `attentionTodayControlHTML()`.
- **Push**: только для `evening-close` и `after-lapse-return`, нейтральная копия без
  названия дела, quote и причины.
- **Locale keys**: `secretary.v2.*` для ru/en/de/uk/es — 24 ключа, сейчас нет ни одного.
- **Action executor** для `task_open_prepared` — открыть запись по `targetRef` и её
  «минимум»; для `size:'minimum'` нужно решить, что показывается, если минимум — это
  `habit.atomic.twoMin`.
- **Обязательный вызов исхода**: `accepted`/`dismissed`/`expired`. Без `expired` серия
  «показали, но не ответили» не наберётся и подавление не сработает.
- **`sw.js` SHELL + `CACHE` bump + пины в тестах** — файл интеграционного владельца.

### Чего этот пакет сознательно не делает

Не подключает маршрут, не правит `app.js`, не добавляет locale-строк, не пишет в сторы,
не трогает `secretary-router-v1.js` и не переключает production engine. «Модуль готов» —
не то же самое, что «функция работает в приложении».

`evals/secretary-next-moves-v2.json` — 50 кейсов, каждый с полем `why`. Прогоняются целиком
