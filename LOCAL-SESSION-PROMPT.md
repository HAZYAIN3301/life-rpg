   результатов (не дефекты).
5. Верх `BACKLOG.md` и `START-HERE.md`.

## Задачи по порядку

### 1. Синхронизировать внешний план

Найди локально папку `satoru-release-plan-20260924/` (START, CHECKPOINT, NEXT,
CRITERIA, EXECUTION). Не угадывай путь: поищи (`mdfind -name satoru-release-plan-20260924`
или в `~/Projects`), а если не нашёл — спроси владельца. Перенеси в CHECKPOINT/START/NEXT
состояние из `RELEASE-CHECKPOINT-R04-R06.md`: пакеты R04A–R12 опубликованы, коммиты,
квитанции, решения владельца, что осталось. Если NEXT.md описывает R05/R06 иначе, чем
выбрал владелец («Экраны + Тень»), отметь расхождение, ничего не переписывай задним числом.

### 2. Автоматический прогон в WebKit (движок Safari)

```bash
npm i --no-save playwright && npx playwright install webkit chromium
PORT=51900 HOST=127.0.0.1 DATA_DIR=./qa-data node server.js   # отдельный терминал
```
Засей синтетические аккаунты и прогони аудиты с `QA_BROWSER=webkit` по
`scripts/qa/README.md`: hidden-audit, dialog-audit, shadow-audit, aisurf-audit,
aisurf-flow, auth-audit, ob-audit. Минимум: RU/EN/DE/UK/ES на 375 (светлая и тёмная
тема) и EN/DE на 1280. Для сравнения прогони те же команды с `QA_BROWSER=chromium`.
Дефект — это то, что есть в WebKit и чего нет в Chromium (или в списке намеренных
результатов). Также проверь в WebKit глазами (скриншоты крупными областями):
«Сегодня» 375, Прогресс (графики R04B), окно недели (R04D), чат Тени, Логово,
Настройки → Интерфейс в светлой теме.

### 3. Проверки на реальных устройствах — вместе с владельцем

Ты не можешь нажимать на телефоне: подготовь владельцу короткий чек-лист, попроси
результаты (скриншоты или «ок/не ок») и запиши их. Микрофон и реальные ИИ-запросы сам
не используешь; ручные проверки владельца — его решение.
- iPhone, Safari и установленная PWA (satoruapp.com): вход и регистрация с VoiceOver —
  поля называются (R12); «Сегодня»; диалоги закрываются, фокус возвращается (R11).
- Экспорт календаря (R04D): файл `.ics` импортируется в Apple Calendar (iPhone/Mac) и в
  Google Calendar; повторный импорт не дублирует события (UID `…@gojo`).
- Картинка «Твоя неделя»: меню «Поделиться» на iOS открывается, PNG сохраняется.
- Диктовка в «Итоге дня» и «Эпизоде» на языке интерфейса (R07) — проверяет владелец.
- Светлая и тёмная тема, крупный шрифт iOS, reduced motion.

### 4. Исправления — только по найденному

Каждый реальный дефект — пакетом по циклу проекта: правка → тест в `scripts/*.test.js`
→ `node --check`, `git diff --check`, полный набор `node --test --test-concurrency=2
scripts/*.test.js` (всё зелёное) → обновить SW-кэш и пины (как в предыдущих пакетах:
`sw.js` CACHE, `PWA_CACHE_VERSION`, `?v=` в index.html и тесты с пинами) → коммит →
fast-forward push в master → дождаться деплоя Railway (`/api/version` на satoruapp.com
и life-rpg-production-416a.up.railway.app) → `scripts/qa/hashcheck.sh <commit> …` →
QA-файл пакета, DEVLOG, BACKLOG, START-HERE, `RELEASE-CHECKPOINT-R04-R06.md`,
внешний CHECKPOINT/NEXT. Если дефектов нет — просто запиши результаты проверок в
`RELEASE-CHECKPOINT-R04-R06.md` и внешний план.

## Границы (от владельца, без исключений)

- Force-push запрещён всегда. Не создавай подагентов, не меняй модель.
- Не работай с личными данными; только синтетические аккаунты в `./qa-data`.
- Не трогай native/iOS-проект, настройки Apple, Documents/Desktop и чужие worktree.
- Не коммить `work/`, `qa-data/`, `qa-accounts/` и локальные доказательства с
  приватными данными.
- Оформление Pro/оплаты не менять до документов владельца.
- Визуальные решения — по конкретным правилам CRITERIA.md; перечисляй применённые.
- Останавливайся только на реальном продуктовом выборе (2–3 варианта с рекомендацией)
  или на неустранимом блокере (провал проверки без очевидного исправления, несовпадение
  хэшей, сбой Railway, небезопасное расхождение с origin/master).
- Отчёты владельцу — коротко, по-русски: было → стало, что проверено (числа), что осталось.
