## Что исправлено

Раньше сервер ставил `raid.claimed`, а браузер отдельно добавлял 150 в lootbox.goldWon.
Потерянный ответ мог оставить отметку без денег. `lb.boost` сохранялся и обещался,
но не читался расчётом XP. Это подтверждённые кодовые дефекты, не утверждение о
потерях в реальном аккаунте. Старые выплаты не пересчитывались и не компенсировались.

Сохранено существующее предложение: **150 монет и +30% XP на 6 часов**. Новый бонус
относится к квестам и привычкам; он входит в прежний общий personal bonus cap 60%,
а не обходится снаряжением/перками. Цели, импортированный XP и эпизоды не усиливаются.
Уже заработанный XP не исчезает с окончанием окна. Нового вида валюты/экрана нет.

## Единственный авторитет

- `public/party-reward-policy-v1.js`: чистые validation/grant/receiptFor/gold/boostPct.
  Время передаётся явно. Окно полуоткрытое `[at, at + 6h)`, не суммируется с другим
  рейдовым окном. Повтор не обновляет `at` или срок.
- `server-party-rewards-v1.js`: dependency-injected synchronous service. Между read
  и durable write нет await. Это контракт нынешнего **single-process** JSON server;
  для нескольких writers нужен transactional DB, не второй Node над тем же томом.
- `data/users/<uid>/party-rewards.json`: `{version:1, receipts:[...]}`. Каждая запись
  сама является ресурсом и квитанцией; нет отдельного счётчика/флага с другой записью.
- Ключ — **account + Monday cycle**, не текущая пати. ID `party:YYYY-MM-DD`, внутри
  `partyId` как происхождение, `at`, `kind`, `gold`, `boost`. UID только из сессии.
- Файл записывается через существующий tempfile → file fsync → rename → dir fsync.
  Если commit случился, но подтверждение пропало, повтор читает прежнюю квитанцию.
  Повреждённые JSON/null/schema не подменяются пустой кассой.
- Баланс добавляет сумму серверных credits к прежней экономике. Ни Store, ни клиент
  не добавляют их ещё раз в `lootbox.goldWon`; legacy wallet не меняется.

## API и совместимость

**⚠️ Ломающее изменение протокола claim для старого клиента.**

- `POST /api/party/claim`: строго `{version:2, cycle}`. Не принимает сумму, uid,
  partyId, выигрыш или дату от клиента. Старый пустой POST получает 409
  `reward_client_update_required` **до** расходования права на награду.
- Успех `{receipt, partyRewards, replay}`; намеренно нет legacy `reward`, чтобы
  старый клиент не добавил серверный credit ещё раз локально.
- Если квитанция уже есть, её можно получить повторно после выхода из пати,
  смены команды и недельного rollover. Новый claim доступен лишь за текущий цикл
  в существующей выигравшей пати. Повтор старой недели не забирает награду новой.
- `GET /api/party/rewards`: свой snapshot; ошибки 503, не мнимая пустота.
  Auth/login/self snapshot также содержит `partyRewards`; чужой публичный профиль — нет.
- `party.raid.iClaimed/claimedCount` выводятся из receipts и legacy markers, а не
  требуют второго авторитетного write в parties.json.
  Новая победа/сезон отдельно фиксируется **до** выдачи, если claim вызван напрямую
  без предварительного GET: этот write не расходует награду и не начисляет монеты.
- PWA cache v250; app pin `20260909-design-v250-1`; новый policy и обновлённый party
  CSS входят в shell. Base/design CSS и старый comparison не изменены.

## Legacy и жизненный цикл данных

До приёма HTTP-запросов сервер переносит **существующие** `raid.claimed` в
`kind:legacy`, `gold:0`, `boost:null`: это запрет повторной выдачи, а не заявление,
что старые деньги действительно дошли. Миграция повторяема; failure блокирует запуск,
чтобы leave/delete не уничтожил единственное свидетельство старого claim.
Существующая новая grant-квитанция никогда не заменяется legacy marker.
Удалённые до этого релиза пати/утраченные старые markers восстановить достоверно нельзя.

- generic `/api/data/party-rewards` запрещён для всех методов, включая restore.
- Account export содержит `serverOwned.partyRewards` как свидетельство **вне** `data`.
  Portable import не восстанавливает из него деньги; попытка положить ledger в `data`
  отклоняется. Импорт прежнего обычного кошелька не уничтожает серверные receipts.
- Удаление аккаунта убирает его user directory с ledger. Полный операторский backup
  DATA_DIR включает ledger; это не переносимый способ выдачи валюты в другой аккаунт.
- Нет данных о содержимом задач, чужих целях или личных текстов. Receipts сохраняются
  на срок жизни аккаунта, поскольку объясняют текущий баланс и прошлый earned XP.

## UI и XP

Одна кнопка в существующем раскрытии рейда. Pending блокирует повторный тап;
таймаут сохраняет cycle и предлагает проверить получение. Ошибка не меняет баланс.
Успех/звук — после receipt, replay не запускает звук новой выдачи. Фокус возвращается
к подтверждению; раскрытие остаётся открытым. Отображается срок действующего бонуса.
Запоздавший snapshot не может откатить уже подтверждённые append-only receipts.
При возврате к вкладке перечитывается snapshot, без сброса открытой формы; reload
восстанавливает его из auth/me. Ошибка обновления сохраняет последнее подтверждённое.

`itemXp` использует timestamp выполнения, либо текущее время для предпросмотра/привычки.
Task/habit XP записывается прежним сохранением (CAS/WAL не обходится). Habit row/toast
показывают записанный `rec.xp`, а не пересчитывают старый результат по текущему бонусу.
Серверные social aggregates также используют окна по `completedAt/rec.at`, перед
дневным anti-abuse cap. Сервер по-прежнему использует свою фиксированную base formula,
а personal XP — прежние настройки/gear/perks; это не новая унификация всех формул.
