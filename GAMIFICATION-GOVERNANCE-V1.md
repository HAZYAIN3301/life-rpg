# Gamification Governance v1 — AG-02 / AG-05 / AG-07 / AG-56

> Невидимый фундамент. Модуль `public/gamification-governance-v1.js` не рисует UI, ничего
> не выключает и не трогает экономику. Он превращает «мы решили, что стало лучше» в
> контракт, который можно проверить.

## Какие карточки аудита он закрывает

| Карточка | Дыра | Чем закрыта здесь |
|---|---|---|
| **AG-02** | Одно слово «conversion» не различает пользу человеку и рост продукта | `metricClass` из трёх значений; North Star обязан быть `user_outcome`, иначе контракт невалиден |
| **AG-05** | Мотивационный контракт нигде не сформулирован целиком | Контракт машиночитаем и печатается человеческим языком через `summarizeFeatureReview` |
| **AG-07** | У поведенческого эксперимента нет pre-mortem и выключателя | `motivationalRisks`, `rollbackPlan`, `owner` и порог `stop` на каждой метрике вреда — обязательные поля |
| **AG-56** | Механика умеет поднять DAU и одновременно навредить | Рост пользы при росте вреда физически не может дать `continue` |

## Границы

Модуль **не**:

- ничего не выключает и не откатывает — статус `stop_recommended` это рекомендация, рычаг у человека;
- ничего не начисляет и не штрафует — экономика вне его словаря;
- не смотрит на часы — `Date.now()` внутри нет, время приходит параметром;
- не трогает DOM, сеть и хранилище — чистые функции, тестируемые из Node.

Автоматический выключатель, встроенный в счётчик, сам стал бы механикой, которую пришлось
бы губернировать. Поэтому суждение и исполнение разделены.

## API

```js
const G = require('./public/gamification-governance-v1.js');   // или globalThis.GamificationGovernanceV1
```

### `defineFeatureContract(input) → contract`

Нормализует любой вход в канонический замороженный контракт. Не судит — мусор на входе
даёт валидную форму с пустыми полями, которую потом отвергнет валидация. Мусор не бросает
исключений: контракт чаще всего собирается из формы, и падать на полпути нельзя.

### `validateFeatureContract(contract) → { ok, errors[] }`

Возвращает **весь** список проблем сразу, отсортированный, а не первую. Коды стабильны и
годятся для привязки к полям формы.

Обязательные поля контракта:

| Поле | Смысл |
|---|---|
| `id` | Идентификатор эксперимента/фичи |
| `humanOutcome` | Что останется у человека ПОСЛЕ выхода из приложения (AG-01) |
| `motivationalBenefit` | Гипотеза пользы: какую мотивацию поддерживаем |
| `motivationalRisks[]` | Pre-mortem. Пустой список = незаполненное поле, не «рисков нет» |
| `northStar` | Главная метрика. Класс обязан быть `user_outcome` |
| `leadingMetrics[]` | Ранние сигналы движения |
| `counterMetrics[]` | Метрики, которые обязаны НЕ ухудшиться |
| `harmMetrics[]` | Вред: сожаление, компульсия, ночные сессии, отписки, обращения |
| `denominatorPolicy` | Основа знаменателя; исключение unknown отключить нельзя |
| `minimumSample` | Ниже этого числа вывода не существует |
| `thresholds` | По метрике: `{ review, stop }`. У каждой метрики вреда `stop` обязателен |
| `rollbackPlan` | Как выключить без миграции данных |
| `owner` | Кто отвечает |
| `phase` | `discovery` / `onboarding` / `scaffolding` / `endgame` (AG-04) |
| `reviewAt` | Дата, к которой контракт обязан быть пересмотрен |

Метрика: `{ id, metricClass, type, direction, baseline, minEffect, label }`.
`type` — `proportion` или `mean`. `direction` — `up_is_good` или `down_is_good`
(у роли `harm` по умолчанию `down_is_good`). `baseline` — значение до раскатки;
без него сравнение просто не делается, вместо выдуманного нуля.

### `calculateMetric(definition, observations) → result`

Наблюдение: `{ subjectId, metricId?, value }`. Без `metricId` строка считается относящейся
к этой метрике.

**Правила знаменателя** (это ядро, а не деталь):

- `null`, `undefined`, `NaN`, `'unknown'`, `'n/a'`, `''`, объекты — **не входят** в знаменатель.
  «Мы не знаем» — это не «не случилось». Посчитать unknown за отрицательный исход значит
  систематически занижать вред.
- Для `proportion` число, отличное от 0 и 1, — тоже unknown, а не «что-то среднее».
- Один субъект = одна строка знаменателя. Повтор с тем же значением не удваивает.
- Известное значение поверх unknown — уточнение, а не конфликт.
- Два **разных** известных значения на один `subjectId` = конфликт, субъект выбывает целиком.
  Не «побеждает последний»: победа последнего сделала бы результат зависимым от порядка
  массива, то есть от случайности.
- `sampleSize === denominator` намеренно: статистическое n — это те, про кого известен
  исход, а не те, кого посмотрели. Общее число видно в `observed`.
- `denominator === 0` → `value: null`, а не `0`. Ноль наблюдений это не «ноль процентов».

Результат: `{ metricId, role, metricClass, type, direction, numerator, denominator,
sampleSize, observed, excludedUnknown, excludedConflicting, excludedForeign, value,
baseline, delta, improved, worsened, reasonCodes[] }`.

### `evaluateFeatureReview(contract, observations, options?) → result`

Бросает `Error` с `code === 'invalid_contract'` и `errors[]`, если контракт невалиден.
Оценивать по неполному контракту нельзя — это и есть та самая дыра.

`options.now` (ISO) необязателен и нужен только для проверки `reviewAt`. Часов внутри нет:
модуль, который сам смотрит на `Date.now()`, перестаёт быть детерминированным, и его
результат нельзя воспроизвести в отчёте.

**Статусы и их приоритет:**

1. `stop_recommended` — метрика вреда перешла порог `stop` **на достаточной выборке**;
2. `insufficient_data` — North Star или любая метрика вреда не набрала `minimumSample`;
3. `review_required` — порог `review`, рост вреда при росте пользы, наступивший `reviewAt`;
4. `continue` — выборка набрана, вред в объявленных границах.

Почему `stop` выше `insufficient_data`: недобор выборки по одной метрике не отменяет уже
увиденный вред на достаточной выборке по другой. Обратный порядок позволял бы прятать
сработавший стоп за «мало данных» в соседней колонке.

Вред, перешедший порог на **недостаточной** выборке, статус не меняет (n=8 это шум, а не
вывод), но обязан быть назван вслух: в `reasonCodes` уезжает
`harm_stop_threshold_crossed_below_minimum_sample:<id>`. Сигнал не теряется.

**Порог засчитывается ровно на границе.** «Стоп при 15%» означает `>= 0.15`, а не
`> 0.15`. Иначе ровно 15% проходило бы молча каждый раз.

**Правило AG-56.** `benefitImproved && harmWorsened` → минимум `review_required`, всегда.
Не важно, насколько хорош рост пользы и насколько мал рост вреда: пока вред растёт,
рост пользы — повод посмотреть, а не повод продолжать. Это единственная защита от
механики, которая «прекрасно работает» и одновременно стоит человеку контроля.

### `summarizeFeatureReview(result) → string`

Детерминированная benefit+harm таблица с владельцем, фазой, планом отката и размерами
выборки. Годится в release report как есть. Пустой знаменатель печатается как `—`, а не
как `0` — цифра, которой нет, не должна выглядеть как цифра.

## Пример

```js
const contract = G.defineFeatureContract({
  id: 'entry-10min',
  humanOutcome: 'Человек делает настоящий маленький шаг вместо откладывания',
  motivationalBenefit: 'Снижает барьер входа, не добавляя давления',
  motivationalRisks: ['Может стать оптимальной валютной фермой'],
  northStar: { id: 'real_step_done', metricClass: 'user_outcome', baseline: 0.40 },
  leadingMetrics: [{ id: 'entry_accepted', metricClass: 'product_health', baseline: 0.20 }],
  counterMetrics: [{ id: 'entry_replaces_real_task', metricClass: 'user_outcome', direction: 'down_is_good', baseline: 0.05 }],
  harmMetrics: [{ id: 'regret_after_session', metricClass: 'user_outcome', baseline: 0.05 }],
  minimumSample: 10,
  thresholds: { regret_after_session: { review: 0.08, stop: 0.15 } },
  rollbackPlan: 'Выключить session-scoped workMin=10 флагом, данные не мигрируют',
  owner: 'Альберт',
  phase: 'scaffolding',
  reviewAt: '2026-10-01',
});

const check = G.validateFeatureContract(contract);   // { ok: true, errors: [] }
const review = G.evaluateFeatureReview(contract, observations);
console.log(G.summarizeFeatureReview(review));
```

## Тесты

`scripts/gamification-governance-v1.test.js` — 29 тестов. Покрыты: нулевой знаменатель,
unknown во всех формах, конфликт по субъекту, малая выборка, границы порогов в обе стороны,
приоритет `stop` над `insufficient_data`, правило AG-56, повторный вызов, независимость от
порядка наблюдений, отсутствие мутации входа и отсутствие рычагов исполнения в экспортах.

```bash
node --test scripts/gamification-governance-v1.test.js
```

## Что дальше (не сделано здесь намеренно)

- Подключение в HTML и любая пользовательская поверхность — зона Codex.
- Хранение контрактов и наблюдений на сервере — отдельная задача; модуль работает и на
  агрегатах, в которых нет ничьих личных наблюдений, и это сознательный выбор формы.
- Связь с телеметрией: события собираются только при согласии
  (см. `TELEMETRY-CONSENT-V1.md`), и `denominatorPolicy` обязана это учитывать — люди,
  отключившие продуктовую аналитику, попадают в `unknown`, а не в знаменатель.
