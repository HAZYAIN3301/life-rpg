# AI Memory Policy v1 — AG-35

> Невидимый фундамент. `public/ai-memory-policy-v1.js` — чистая политика памяти
> ассистента; эндпойнты в `server.js` дают ей диск и границу аккаунта. UI нет — это
> зона Codex.

## Карточка аудита

**AG-35** — «Personalization должна быть explainable, editable и portable». Дыра:
полезная память тихо превращается в поведенческое досье. Человек не знает, откуда
Тень взяла утверждение о нём, и не может его поправить, не снося аккаунт. Все три
обещания держатся на одном: у каждой записи есть названный источник.

## Что уже было и что здесь НЕ переделано

Память ассистента живёт в `users/<uid>/profile.json` и состоит из свободного текста,
который ведёт [`profile-memory-v1`](public/profile-memory-v1.js): ИИ переписывает,
человек правит, бюджет 3000 символов. **Этот текст остался ровно там же, в том же
файле и в том же поле.**

Второго источника правды нет намеренно: два места для ответа на вопрос «что Satoru обо
мне помнит» — это два разных ответа, и человек никогда не узнает, какой настоящий.
Модуль добавляет в тот же файл массив `entries` — структурные записи, у которых до сих
пор не было своего места, — и **читает** старый текст, не мигрируя и не переписывая его.

Форма файла после этого:

```json
{
  "text": "...свободный профиль, как и раньше...",
  "updatedAt": "2026-09-01T10:00:00.000Z",
  "auto": true,
  "schemaVersion": 2,
  "entries": [ { "id": "...", "sourceType": "explicit", ... } ]
}
```

`schemaVersion: 1` (или его отсутствие) = старый файл без записей. Это валидное
состояние, а не поломка.

## Границы

Модуль **не**: не ходит в сеть, не трогает DOM и `localStorage`, не смотрит на часы
(время приходит в операции), не начисляет ничего. Он не отправляет память в модель —
он только говорит, что можно отправить и почему.

## Правила, исполняемые механически

| Правило | Как исполнено |
|---|---|
| Явное старше выведенного | `SOURCE_TYPES` упорядочены `explicit > imported > inferred`; порядок = приоритет в сортировке и в разрешении дублей |
| Вывод не перезаписывает явное | `upsert`/`update` с `inferred` поверх не-`inferred` → `inferred_cannot_overwrite_explicit` |
| Чувствительное нельзя создать выводом | `inferred` + `sensitive` → `sensitive_inference_rejected`; такая пара отбрасывается даже при чтении с диска |
| Убранное не попадает в промпт | `status !== 'active'` → `excluded: [{ reason: 'dismissed' }]` |
| Каждая запись объясняет себя | `explainMemoryEntry` даёт `origin` и `usage` человеческим языком; `selectMemoryForPrompt` возвращает `selectionReason` у вошедших и причину у **не** вошедших |
| Старое читается без миграции | `legacy.text` переносится дословно и никогда не разбирается на записи |
| Правка одной записи не трогает профиль | сервер пишет только `entries` + `schemaVersion`; `text`/`updatedAt`/`auto` переносятся байт в байт |

## Запись

```js
{
  id, schemaVersion,
  text,                              // ≤400 символов
  category,                          // identity | preference | constraint | pattern | goal_context | history | other
  scopes: [],                        // assistant_prompt | planning | reflection | shadow_voice
  sourceType,                        // explicit | imported | inferred
  sourceRef,                         // что именно её породило — видно человеку
  confidence,                        // 0..1; у explicit всегда 1
  sensitivity,                       // normal | sensitive
  status,                            // active | dismissed
  createdAt, updatedAt,
}
```

Пустой `scopes` — законное состояние «помню, но не рассказываю».

## API

```js
const M = require('./public/ai-memory-policy-v1.js');   // или globalThis.AiMemoryPolicyV1
```

### `normalizeMemoryStore(input) → store`

Читает `profile.json` в любой форме: старую (только текст), новую (текст + `entries`),
архив экспорта, голую строку.

**Fail-safe в два уровня** — и это не перестраховка:

- `damaged: true` — файл не разобран вообще. Читать нечего, **писать нельзя**.
- `dropped: N` — часть записей нечитаема. Уцелевшее показываем, но писать всё равно
  нельзя: перезапись потеряла бы непрочитанное навсегда.

`safeToWrite` ложь в обоих случаях. Пустой результат никогда не выдаётся за «памяти нет»
— это означало бы «ты ничего не рассказывал» и разрешило бы затереть настоящие записи.

### `applyMemoryOperation(store, operation) → { ok, reason, store, entryId }`

Возвращает **новый** store; вход не мутируется (и не замораживается — отказ не имеет
права трогать объект вызывающего). `operation.at` (ISO) обязателен: часов внутри нет.

Операции: `create` · `upsert` · `update` · `dismiss` · `restore` · `delete`.

`update` принимает только `text`, `category`, `scopes`, `sensitivity`, `status`.
`sourceType`, `confidence` и `createdAt` не патчатся: их меняет не человек, а сам факт
правки.

**Человек, поправивший вывод, делает запись своей.** `actor: 'user'` (умолчание)
переводит запись в `explicit`, `confidence: 1`, `sourceRef: 'user_edit'`. Именно это
делает ошибочный вывод исправимым без сноса аккаунта — обещание AG-35 одной строкой.

Причины отказа: `store_not_writable`, `sensitive_inference_rejected`,
`inferred_cannot_overwrite_explicit`, `not_found`, `duplicate_id`, `invalid_entry`,
`invalid_patch`, `invalid_operation`, `invalid_operation_time`, `too_many_entries`,
`unknown_op`.

### `selectMemoryForPrompt(store, context) → selection`

`context = { scope, limit?, maxChars?, allowSensitive? }`.

Возвращает и то, что вошло, и то, что **не** вошло, с причиной. Список исключённых — не
отладка: без него «почему Тень этого не знает» остаётся без ответа ровно так же, как
«откуда Тень это взяла».

Причины исключения: `dismissed`, `out_of_scope`, `sensitive_not_allowed`,
`superseded_by:<id>`, `limit_reached`, `budget_exhausted`.

**Чувствительное уходит в модель только по явному `allowSensitive: true`.** Умолчание
«не отправлять» важнее удобства: отправить один раз нельзя отменить.

Бюджет режется по целым записям — обрезанная на полуслове память врёт сильнее, чем
отсутствующая. Старый свободный текст отдаётся отдельным полем `legacyText` и дословно:
для старых пользователей ассистент обязан работать ровно как раньше.

### `explainMemoryEntry(entry) → explanation | null`

`origin` человеческим языком («Вы сказали это сами (settings_form)», «Посчитано
программой по вашим данным (weekly_pattern_detector)»), `usage`, `selectionReason`,
`editable`/`deletable` — всегда `true`: память, которую нельзя убрать, это досье.

### `exportMemory(store) → archive`

`normalizeMemoryStore(exportMemory(store))` возвращает тот же store. Переносимость без
round-trip — это обещание, а не свойство.

## Эндпойнты

Все требуют сессию и работают строго в границах своего аккаунта.

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/api/ai/memory` | `{ entries: [explained], legacy, schemaVersion, partial }` |
| `GET` | `/api/ai/memory/export` | архив `satoru-ai-memory` |
| `PATCH` | `/api/ai/memory/:id` | `{ op: 'update'\|'dismiss'\|'restore', patch? }` → `{ ok, id, entry }` |
| `DELETE` | `/api/ai/memory/:id` | `{ ok, id, entry: null }` |

Коды: `401` без сессии · `404` нет такой записи · `409` политика запретила
(`sensitive_inference_rejected`, `inferred_cannot_overwrite_explicit`) · `422`
`invalid_memory_state` / `store_not_writable` · `405` иначе.

`actor` всегда `'user'` — это владелец через свою сессию. Позволить телу запроса
назваться `'system'` значило бы отдать клиенту право писать выводом; тест это проверяет.

**Экспорт и удаление аккаунта подхватывают память сами.** `profile` уже в
`ACCOUNT_PORTABLE_FILES`, а каталог пользователя целиком уезжает в
`deleteAccountLifecycle`. Отдельной проводки память не требует и не получает — это
прямое следствие решения не заводить второй файл.

### Вторая дверь в тот же файл

Тот же `profile.json` пишется ещё и общим путём `PUT /api/data/profile` — через него
`app.js` сохраняет карточку профиля. Про политику памяти он не знает: его валидатор
`account-data-v1` проверяет только форму объекта и пропускает любые дополнительные поля,
включая `entries`.

Опаснее всего тут не сама плохая запись — её отбросят при чтении, — а то, что из-за неё
файл считается прочитанным не полностью и **закрывается на запись целиком**: человек
теряет возможность отредактировать и удалить свои нормальные записи.

Поэтому на общем пути стоит замок с простым правилом: **если политика не может прочитать
всё, что ты пишешь, ты этого не пишешь.** Запись с `entries` прогоняется через
`normalizeMemoryStore`, и `damaged` или `dropped > 0` дают `400 invalid_memory_entries`.

Профиль **без** `entries` проходит нетронутым — это обычный старый файл, и сегодняшние
сохранения карточки из `app.js` работают как работали. Спред `{ ...prof, text, … }`,
который там используется, проносит `entries` насквозь; тест это фиксирует, потому что
переход на «собрать объект профиля с нуля» стёр бы память.

## Тесты

```bash
node --test scripts/ai-memory-policy-v1.test.js scripts/ai-memory-server-v1.test.js
```

- `scripts/ai-memory-policy-v1.test.js` — 25 тестов: чтение legacy без миграции,
  fail-safe обоих уровней, запрет sensitive-вывода, запрет перезаписи explicit, правка
  человеком → explicit, `dismissed` мимо промпта, scope, дубли, бюджет,
  детерминированность, round-trip экспорта, отсутствие мутации входа.
- `scripts/ai-memory-server-v1.test.js` — 12 тестов: чужая память недосягаема,
  объяснения в ответе, правка/удаление не трогают профиль, соседей, цели и настройки,
  повреждённый файл не перезаписывается, sensitive-вывод не отдаётся, валидация PATCH,
  экспорт памяти и аккаунта, удаление аккаунта уносит память (включая резервные копии),
  общий путь записи не пускает память мимо политики, карточка профиля сохраняется поверх
  памяти не теряя её.

## Integration contract для Codex

- Модуль в HTML **не подключён**, UI памяти не нарисован.
- **Создание записей идёт только через `applyMemoryOperation`.** Общий путь
  `PUT /api/data/profile` ведёт в тот же файл, поэтому на нём стоит замок (см. ниже):
  запись, которую политика не может прочитать целиком, отклоняется с
  `400 invalid_memory_entries` и на диск не попадает.
- Клиент, сохраняющий карточку профиля, **обязан сохранять форму `{ ...prof, text: … }`**
  (как сейчас и делает `app.js`), иначе спред потеряет `entries`.
- `MAX_PROMPT_CHARS` — бюджет только структурной части. Свободный текст живёт по своему
  бюджету в `profile-memory-v1`; складывать их в одно число нельзя.
